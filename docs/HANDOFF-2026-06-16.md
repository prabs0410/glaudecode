> ### ⟳ UPDATE (same day, continued session) — mirror inconsistency root-caused + fixed (test-first pass)
> A 10-agent verification workflow traced the whole output pipe and **code-confirmed** the cause: it's not one
> bug but several that compound, clustering on **two triggers — an engine (Bun sidecar) respawn and a high-output
> burst (the `yes` flood), and the flood can cause the respawn.** The dominant structural defect:
> **each PTY reader thread captured a one-time snapshot of the bridge sender** (`lib.rs`), and the output pump
> had **no stop flag** — so after any engine respawn, every pane opened *before* it teed into the dead channel
> forever and went **permanently blank**, while panes opened *after* rendered fine (and the keyboard kept
> working, because the *input* bridge **is** rebuilt on respawn). Two ACK/flow-control hypotheses were
> **refuted** as blank causes (they self-heal) and not "fixed" as bugs.
>
> **Shipped (branch `fix/v5-audit`, 3 commits, all gates green):**
> - **Rust `7a8f795`** — reader threads resolve the *current* sender per chunk (respawn-transparent); output
>   pump gets a stop flag retired on respawn; engine exit/respawn/down logged to stderr (so we can *see* the
>   trigger fire in `tauri dev`).
> - **Engine `feb095d`** — `PaneHub.resyncStalled()` (server-driven recovery, no client-ACK gate) force-repaints
>   a sub stuck `lagging` after ~2 sweeps; `setSize` no longer wipes a lagging sub's xterm. +2 tests.
> - **Phone `18290d6`** — `connect()` resets ACK counters + `term.reset()` on reattach; 4002 re-lists panes
>   instead of looping a dead id; single-socket hygiene kills the background↔foreground dup-socket race.
>
> **Deferred to "iterate" (chosen scope = test-first):** the Rust-owned per-pane screen ring replayed on bridge
> reconnect (the full fix for an *idle* pane after respawn) + flood coalescing — only if blank persists on the
> real device. **NEXT: founder device-test on the phone** (see the test script in §3). Full diagnosis with
> file:line + adversarial verdicts is in the workflow output; ranked causes are #1 respawn-orphan (fixed),
> #4 empty-ring-on-respawn (mitigated by clear-on-reattach + #1), #5 flood-drops (deferred coalescing).

### B. Live mobile-UX debugging — 4 real bugs found + fixed
These are NOT audit findings; they surfaced while the founder tested on a real phone. (The founder's idea to
test the served pages in a **laptop browser** is what cracked the big one.)
- **`f7d234e` Tailscale-Serve UI freeze** — `tailscale_serve_start` was a *sync* Tauri command → ran on the
  main thread; `tailscale serve --https=443` blocks (and stalls when HTTPS certs are off) → froze the whole
  app. Made it `async` + `spawn_blocking` + timeout-bounded; on failure it falls back to the plain tailnet-IP
  bind (works without certs).
- **`580f08f` pair-modal layout broken** — `.pair-gen` was a horizontal flex row, so the terminal-scope
  warning crushed into a sliver and shoved "Generate code" off the modal edge. Stacked it vertically.
- **`d277ef7` THE BIG ONE: the phone input bar never rendered for anyone.** `#inputbar`'s CSS default is
  `display: none`, and the code "showed" it with `bar.style.display = ""` — which reverts to the CSS rule
  (`none`). So the Message/Keys/Smart bar + key bar never appeared. Shipped uncaught because Phase-4's
  device-QA was a deferred human gate. Fix: explicit `display: block`. Verified end-to-end in a headless
  browser (173px tall, full key bar; was `display:none`/`offsetHeight:0`).
- **`ad11ce9` self-inflicted: scopenote string broke the whole served script.** The "view-only → how to fix"
  message I added (`580f08f`) used `\"` inside termPage's **template literal**, which collapses to a bare `"`
  in the served JS → syntax error → the entire inline script failed to parse → **blank page, grey dot, no
  pill.** Removed the escaping; added a **parse-guard test** (extracts every inline `<script>` and asserts it
  parses) so a broken served page can never ship green again.

## 5. Load-bearing facts & gotchas for next session

- **Git:** branch `fix/v5-audit` off `feat/v5-governance`. Commits MUST be **`prabs0410`** (local
  `user.email 192090657+prabs0410@...`), no AI co-author lines. Run `git` from the **repo root** (cd-into-package
  then `git add` doubles the path). Never commit to `main`.
- **Engine changes need an app restart.** The Bun engine sidecar respawns on app launch; the phone-served
  pages (`cockpit.ts`, `termPage.ts`) only update then. Desktop TS/CSS hot-reloads via vite, but the phone
  page does **not**. Each restart = a **new engine port** + the phone must **re-pair**.
- **The served phone pages are TypeScript template literals.** A `\"` inside breaks the whole script (this bit
  us — `ad11ce9`). The new `termInput.test.ts` parse-guard catches it. To get a literal backslash-escape in the
  served JS, double it (`\\"`), or just avoid escaped quotes.
- **Testing mobile UX without a phone (the winning recipe):** use the gstack **`/browse`** skill. Fetch the
  served term page (`curl localhost:<port>/app/term`), build a harness: remove the `<script src=/app/xterm.js>`
  and prepend a `<head>` stub that (a) `sessionStorage.setItem('ck.token','x'); setItem('ck.scope','terminal')`,
  (b) stubs `window.Terminal` (xterm throws headless), (c) stubs `fetch` to return `{result:{...}}` for `/rpc`
  (else the page 401→redirects), (d) stubs `WebSocket`. Then `goto file:///tmp/harness.html?pane=X` and inspect.
  Or extract the live source via `bun -e "import {TERM_HTML} from './src/termPage.ts'; await Bun.write(...)"`.
  CDP `addScriptToEvaluateOnNewDocument` is **denied** by browse's allowlist.
- **Multi-engine mess:** the dev `tauri dev` watcher relaunches the app on Rust rebuilds and leaves **orphaned
  engine sidecars**. The phone can pin to a stale one. `pgrep -f engine/bin/serve.ts` to see them; the
  `.glaudecode/approval-endpoint.json` token is **often stale** (points to a dead engine). You **cannot mint a
  pair code without the local bearer** — that's the M3 hardening working; for browser testing, stub
  sessionStorage instead.
- **The `y`-flood was `yes`, not a bug.** Typing `yes` at a shell prompt runs `/usr/bin/yes`; stop it with `^C`
  (phone key bar) or Ctrl-C (Mac).
